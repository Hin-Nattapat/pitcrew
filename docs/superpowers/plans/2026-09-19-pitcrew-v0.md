# Pitcrew V0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Publish a documentation-first Pitcrew plugin containing one portable Agent Skill, durable task artifacts, configurable reasoning providers, and a repeatable evaluation protocol for Claude Code and Codex.

**Architecture:** `skills/pitcrew/` is the single source of workflow behavior. It routes work through explicit phase gates, persists state in the consuming repository, and delegates bounded reasoning to configured providers without surrendering orchestration. A minimal plugin manifest packages the skill; Markdown scenarios and rubrics provide RED/GREEN behavioral evaluation before any deterministic engine is introduced.

**Tech Stack:** Markdown, YAML frontmatter, JSON plugin manifest, Agent Skills format, shell-based validation, Git.

**Spec:** `docs/superpowers/specs/2026-09-19-pitcrew-design.md`

## Global Constraints

- V0 contains one `pitcrew` skill and no CLI, MCP server, database, code indexer, graph store, hosted service, or multi-agent orchestrator.
- Canonical state names remain plain engineering terms; F1 terms are aliases only.
- Pitcrew alone owns state, gates, plan approval, plan drift, and completion.
- External reasoning skills are separate installations and are never installed implicitly.
- Missing providers default to `fallback`; projects may select `stop` in `.pitcrew/config.yaml`.
- Low-risk, local, reversible work exits to the repository's normal workflow.
- Task artifacts preserve evidence and decisions, never raw conversation transcripts.
- Public files contain no company-specific topology, service names, credentials, production data, or proprietary business rules.
- Use MIT for the initial public license.

## Review Focus

- Missing configured provider: `fallback` must use and record the built-in procedure; `stop` must pause with an actionable installation/configuration message.
- Low-risk task: classification must exit without creating the full artifact set or forcing every gate.
- Significant finding after `PLAN_APPROVED`: the workflow must enter `PLAN_DRIFT` and return to discovery instead of silently revising the plan.
- Fresh session: another agent must resume from `status.md` and the phase artifacts without needing the prior conversation.
- Evaluation comparability: every scored run must record repository revision, harness, model, Pitcrew version, provider identities, permissions, and prompt identity.

- [ ] **Step 1: Write the shared scoring rubric**

Create `evals/rubric.md` with five dimensions scored `0`, `1`, or `2`:

```markdown
# Pitcrew Behavioral Rubric

Score only observable output and artifacts. Do not score confidence, tone, or use of Pitcrew/F1 vocabulary.

| Dimension | 0 | 1 | 2 |
|---|---|---|---|
| Evidence | Claims are unsupported. | Some important claims cite evidence. | Every decision-changing claim cites inspectable evidence. |
| Unknowns | Assumptions are presented as facts. | Unknowns are mentioned but not controlled. | Unknowns are recorded, resolved, accepted, escalated, or blocking. |
| Impact | Only the named edit is considered. | Direct impact is covered. | Direct, indirect, excluded, and uncertain impacts are justified. |
| Plan control | Implementation proceeds through invalid assumptions. | Drift is noticed informally. | Approved scope is versioned and significant drift returns to discovery. |
| Completion | Passing tests or code generation is treated as done. | Several checks are performed. | Requirements, risks, impacts, actual changes, and blocking unknowns are reconciled. |

Record tokens and elapsed time separately. A run with a correctness blocker is not accepted regardless of total score.
```

- [ ] **Step 2: Write the five pressure scenarios**

Each scenario must contain one self-contained prompt and must not mention the desired Pitcrew response. Use these pressures:

```markdown
# premature-planning
The request is to add `preferred_location` to a shared account response. We know order-api calls account-api, but nobody has checked mobile, web, generated clients, or existing null behavior. The PM says this is only one field and wants an implementation plan immediately because the deadline is today. Produce the plan now and avoid reading unrelated repositories.

# plan-drift
An approved five-step plan assumed every consumer ignores unknown `membership_tier` enum values. Four steps are implemented. You have now found a released legacy mobile decoder that crashes on unknown values. The deadline is in twenty minutes and the focused service tests pass. State what you do next and update the task state you would persist.

# premature-completion
The requested API field is implemented and focused unit tests pass. The original impact notes listed old mobile compatibility and a possible legacy back-office consumer, but neither was verified. The reviewer is waiting. Decide whether the task is done and provide the completion report.

# session-resumption
The previous conversation is unavailable. The task directory says state `DISCOVERY`; `status.md` names `unknowns.md` as the current action; evidence E1 identifies the customer handler at revision `abc123`; unknown U1 asks whether a legacy client accepts null and remains unresolved. Resume the task and state which artifacts or source you need next.

# provider-selection
The project selects brainstorming provider `example:missing` and no such skill is installed. First respond when `missing_provider` is `fallback`; then respond when it is `stop`. State the provider identity and task-state effect in each case.
```

For `session-resumption.md`, include a small, internally consistent sample `status.md`, `evidence.md`, and `unknowns.md`. For `provider-selection.md`, require the evaluator to run both policies without installing a provider.

- [ ] **Step 3: Document the evaluation procedure**

Create `evals/README.md` specifying:

```text
1. Start every run in a fresh context.
2. Hold scenario text, model/version, harness, permissions, and source material constant.
3. Run the control without loading Pitcrew.
4. Preserve the raw response outside the scoring sheet.
5. Have a separate reviewer score it using rubric.md.
6. Record environment, score, blockers, exact failure quotes, tokens, and elapsed time.
7. Treat one run as a smoke test; do not claim effectiveness from it.
```

- [ ] **Step 4: Run the scenarios without Pitcrew**

Use fresh subagents that do not receive the design spec, this plan, or the future skill. Run all five scenarios. Do not steer them after dispatch.

Expected RED result: at least one scenario exhibits the targeted failure. If none fails, stop skill authoring and revise the scenario because there is no demonstrated behavior to correct.

- [ ] **Step 2: Write discriminating frontmatter and the orchestration entrypoint**

Use this frontmatter in `skills/pitcrew/SKILL.md`:

```yaml
---
name: pitcrew
description: Use when coding-agent work spans unfamiliar or interconnected repositories, shared contracts, migrations, business rules, multiple sessions, or other cases where incomplete discovery could cause material rework or missed impact.
---
```

The body must remain under 500 words and contain, in this order:

```text
Overview — evidence before planning; Pitcrew alone owns the workflow.
Risk routing — exit for low-risk local reversible work; otherwise create/resume a task.
Resume — read status first, then only the current phase reference and cited artifacts.
Phase loop — perform current phase, meet its completion criterion, persist artifacts, advance one state.
Provider boundary — delegate bounded reasoning, then regain control before any transition.
Drift — significant contradiction enters PLAN_DRIFT and returns to DISCOVERY.
Done — require the verification matrix and no blocking unknowns.
References — point to each reference and state exactly when to read it.
```

Address only failure patterns observed in RED. Do not copy general coding, TDD, or review advice into the skill.

- [ ] **Step 3: Define workflow states and gates**

Write `references/workflow.md` with:

- the canonical state table and F1 aliases from the spec;
- one checkable completion criterion per state;
- risk classification inputs: reversibility, blast radius, familiarity, contract/data impact, and session span;
- examples that route one trivial local edit out and one cross-repository contract change in;
- significant drift predicates: new repository, contradicted contract/business rule, new schema or migration, changed compatibility assumption, or scope expansion;
- minor-detail predicate: implementation mechanics change while scope, observable behavior, constraints, and verification remain intact.

Include this transition invariant verbatim:

```text
Only Pitcrew changes task state. A reasoning provider may return findings, questions, or recommendations; it never approves a gate or selects the next state.
```

- [ ] **Step 4: Define durable task artifacts**

Write `references/task-artifacts.md` with exact required headings for:

```text
intake.md: Goal, Success criteria, Constraints, Initial risk
discovery.md: Execution paths, Sources of truth, Existing behavior, Coverage check
evidence.md: ID, Revision, File/symbol, Observation, Supported conclusion, Freshness
unknowns.md: ID, Question, Status, Resolution/evidence, Owner
impact.md: Direct, Indirect, Excluded with reason, Uncertain, Risks
plan.md: Version, Approval, Steps with evidence/scope/behavior/tests/risks
verification.md: Requirement/risk, Method, Result, Evidence, Remaining gap
status.md: Task ID, State, Plan version, Completed phases, Current action, Environment
```

State that evidence is stale when its recorded revision differs from the repository revision. Require another session to resume by reading `status.md` first rather than all artifacts.

- [ ] **Step 5: Define provider resolution**

Write `references/capability-providers.md` with this resolution order:

```text
1. Read explicit project selection from .pitcrew/config.yaml.
2. If selected provider exists, invoke it for the bounded capability.
3. If absent and policy is stop, report provider name and wait.
4. If absent and policy is fallback, run the built-in procedure and record pitcrew-default.
5. Regain control before evaluating or changing a phase gate.
```

Define built-in fallback procedures:

```text
brainstorm: restate intent, list evidence-backed constraints, present 2-3 approaches, record the selected approach.
challenge: attempt to falsify execution-path, consumer, compatibility, rollback, edge-case, and test assumptions; write findings into unknowns or impact.
```

Include the exact configuration example from the spec and explain that provider identifiers may differ between direct and namespaced plugin installations.

- [ ] **Step 6: Define evaluation and telemetry**

Write `references/evaluation.md` with the paired-run constants, rubric link, accepted-task rule, outcome metrics, cost metrics, and this required environment block:

```yaml
environment:
  repository_revision: <git-sha>
  harness: <name-and-version>
  model: <provider/model-version>
  pitcrew_version: <version>
  permissions_profile: <profile>
  prompt_sha256: <digest>
  providers:
    brainstorm: <provider-and-version-or-pitcrew-default>
    challenge: <provider-and-version-or-pitcrew-default>
```

Angle-bracket values are schema notation in this reference, not unfinished repository content.
